# yue2-server implementation plan

HTTP job server that serves the YuE2 song-generation model (`../YuE`, package `yue2-infer` 0.1.6) in Python.
It follows the shape of `../qwen-image-server`: load the pipeline once, queue JSON requests, run them one at a
time on the GPU, and serve the results by job id. It is meant to sit behind `../simple-ai-router` as a
job-queue model (`busyCheck` on `GET /health`).

## 0. Concepts: what runs when a song is generated

Source: the [model overview](https://map-yue2.github.io/#model-overview), `../YuE/README.md`, and the model
configs in `../YuE/models/*/config.json`.

**Two checkpoints, three model stages, four data representations.**

```
style + lyrics (text)
   │  tokenized with the Qwen tiktoken vocabulary (184,704 tokens incl. ABC/music markers)
   ▼
┌──────────────────────────────── YuE2-3B  (one checkpoint, 6.8 GB, bf16) ─────────────────────────────────┐
│  AR–NAR Mixture-of-Transformers: 28 layers, hidden 2048, ~3.59 B params.                                 │
│  The AR expert and the NAR expert share one attention computation per layer but have separate           │
│  norms, projections and MLPs. Same weights file, two "personalities".                                    │
│                                                                                                           │
│  Stage 1  AR planner      text ──► ABC score (editable melody + chords)           ["Planning score"]      │
│  Stage 2  AR generator    text + ABC ──► semantic tokens (codec ids, 32,768 vocab) ["Generating song"]    │
│  Stage 3  NAR expert      semantic tokens ──► acoustic latents [T, 64] via flow matching,                 │
│                           32 midpoint ODE steps, seeded CPU noise               ["Synthesizing audio"]   │
└───────────────────────────────────────────────────────────────────────────────────────────────────────────┘
   │  latents: 64-dim frames, 1 frame = 1920 samples = 40 ms at 48 kHz
   ▼
┌──────────────────────────────── YuE2-Vae (second checkpoint, 507 MB, fp32) ──────────────────────────────┐
│  Stage 4  Oobleck VAE decoder (stable-audio-tools lineage), decoder-only at inference,                    │
│           tiled with 1024-frame cores and 16-frame halos               ["Decoding audio"]                 │
└───────────────────────────────────────────────────────────────────────────────────────────────────────────┘
   │
   ▼
48 kHz stereo audio (FLAC, 24-bit)
```

Notes on the count:

- Stages 1 and 2 are the same AR expert called twice with different prefixes (the ABC generation ends with
  an `ABC_END` marker, then `MUSIC_START` opens the semantic phase). Stage 3 is the NAR expert of the same
  network. So "3 models" is right if you count experts by function (AR, NAR, VAE) and wrong if you count
  files (2). The server only ever loads two checkpoints.
- `cot` selects how much of stage 1 runs: `full` plans melody and chords, `melody` plans only melody, `off`
  skips planning and goes straight to semantic tokens. Supplying `abc` replaces stage 1 with your own
  score (tokenized, never generated).
- `YuE2-Vae-legacy` is an alternative stage-4 decoder used for the published benchmark numbers. Same
  latents, different decoder; it can be swapped in without regenerating stages 1–3.
- **MERT2** (music encoder) and **SheetSage2** (audio-to-score transcription) are separate models with
  their own dependency pins. MERT-v2-FullSong is a 632M bidirectional encoder: 24 kHz mono in, one 1,024-dim
  feature per 40 ms out, on songs of 30–360 s. "FullSong" means full-song context, not song continuation;
  it never generates or extends audio. MERT2 was used to derive the semantic tokenizer and SheetSage2 to produce
  symbolic training targets. At inference SheetSage2 is only needed for the *cover* workflow (transcribe a
  recording to ABC, feed it in as `abc`). Neither is loaded by `YuE2Pipeline`.
- Classifier-free guidance (`cfg_scale`) runs stage 2 with a second, negative prefix (instruction only, or
  instruction plus the same ABC) and combines the logits. Default is effectively off (1.0; 1.01 for `off`).

**Input modes.** YuE2-3B accepts only text and ABC. There is no audio input, no reference-voice prompt, and
the pipeline loads the VAE decoder-only, so a recording cannot be encoded.

| Task | Inputs to YuE2 | Where the score comes from |
|---|---|---|
| Text → audio | style, lyrics, `cot=full/melody/off` | generated by stage 1 (or none for `off`) |
| Score → audio (edit) | style, lyrics, `abc`, `cot=full/melody` | a saved plan, edited by a person or agent |
| Audio + text → audio (cover) | style, new lyrics, `abc`, `cot=melody` | SheetSage2 transcribes the recording to melody-only ABC first |

The source recording influences a cover only through its transcribed melody; timbre, voice and mix are never
copied. SheetSage2 runs in its own environment (torch 2.8, transformers 4.45); the server runs it as a
subprocess job in the same queue so it shares the GPU sequentially with YuE2.

**Workflows from the yue2-music skill, mapped onto the server API.** The skill's `SKILL.md` lists these
workflows; every one of them reduces to `POST /jobs` with a `task` and a `cot`, plus ABC handling on the
client side.

| Skill workflow | Server calls |
|---|---|
| Generate with editable melody and harmony | `POST /jobs {task: generate, cot: full}` → `/score` and `/audio` |
| Generate with a melody plan and free accompaniment | `POST /jobs {task: generate, cot: melody}` |
| Generate without symbolic planning | `POST /jobs {task: generate, cot: off}`; no `/score` |
| Change harmony, instruments, tempo, structure, or lyrics | `POST /jobs {task: plan}` → edit ABC/text → `POST /jobs {task: generate, abc, cot: full}` |
| Cover an ABC melody | strip chords client-side → `POST /jobs {task: generate, abc, cot: melody}` |
| Cover a recording | `POST /jobs/transcribe` (multipart audio) → strip chords client-side → `POST /jobs {task: generate, abc, cot: melody}` |
| Agentic editing | plan → agent edits → `abc_tools.py` invariant checks → audio job → compare `result.json` identities |
| Analyze musical features (MERT2) | out of scope; MERT2 is not part of generation |

The chord-stripping and invariant checks live in the skill's stdlib-only `abc_tools.py`. Those stay on the
client side or in the agent, not in the server, so the server's job stays "run the two checkpoints".

What this means for the server:

| Stage | Where time goes | Progress signal available | Cancellable |
|---|---|---|---|
| 1 ABC | AR decode, up to 4096 tokens | `on_token` per token | yes |
| 2 semantic | AR decode, up to 9000 tokens, ×2 with CFG | `on_token` per token | yes |
| 3 NAR | 32 ODE steps per context chunk, one AR prefill per chunk | none public (stderr `Progress` only) | yes, per step |
| 4 VAE | tiled conv decode, seconds | none public | no |

Between stage 2 and 4 the pipeline moves the 3B model to CPU and the VAE to GPU, and back for the next job.

## 1. What the YuE project gives us

Findings from reading `../YuE/src/yue2/` and the two bundled skills.

**Pipeline API** (`yue2.pipeline.YuE2Pipeline`)

- `YuE2Pipeline.from_pretrained(model, vae=..., device=..., memory_budget_gib=24, backend="torch",
  quantization="none", local_files_only=..., progress=...)` verifies weight hashes and builds the tokenizer.
  The 3B MoT model loads lazily on the first generation; the VAE decoder loads lazily on the first decode.
- `pipe(style=, lyrics=, cot=, seed=, abc=, cfg_scale=, id=, abc_sampling=, semantic_sampling=,
  cancelled=, on_token=)` runs the four stages and returns a `SongResult` with 48 kHz stereo float audio.
- Staged calls exist too: `plan()` → `generate_semantic()` → `synthesize()` → `decode()`. `plan()` alone
  is the cheap "give me an editable score" step.
- `SongResult.save_artifacts(dir)` writes `audio.flac`, `score.abc`, `plan.json`, `semantic.npy`,
  `latent.npy`, `request.json`, `config.json`, `result.json` with SHA-256 manifests. `result.json` carries
  `identity` (hash of request + config + weights), `truncated` flags, `audio_seconds`, and per-stage timing.
- **Hooks we can use**: `on_token(phase, token)` fires once per generated token in the `abc` and `semantic`
  phases. `cancelled()` is polled during ABC generation, semantic generation, and NAR synthesis
  (raises `InterruptedError`). There is no cancel hook inside VAE decode, and no public step callback for
  NAR/VAE progress (they only report through the stderr `Progress` object when `progress=True`).
- **Concurrency**: the CLI's `batch` command refuses `concurrency != 1`. One pipeline, one job at a time.
- `decode()` moves the MoT model to CPU and the VAE to GPU; the next generation moves the MoT back. So every
  job pays two ~7 GB PCIe transfers. Acceptable; noted for ETA.
- The pipeline sets `torch.cuda.set_per_process_memory_fraction` from `memory_budget_gib` (budget minus
  2 GiB reserve, capped at total minus 2 GiB).

**Request protocol** (`yue2.protocol.SongRequest`)

| Field | Type | Notes |
|---|---|---|
| `style` (alias `tags`) | str | required |
| `lyrics` | str | required, with `[Verse]` / `[Chorus]` section tags |
| `cot` | `full` \| `melody` \| `off` | default `full` |
| `seed` | int in [0, 2^63) | default 831001 |
| `abc` | str or null | supplied score; requires `cot` = `full` or `melody` |
| `cfg_scale` | float in [0, 20] or null | default 1.0 (1.01 for `off`) |
| `id` | filename-safe str | default `song`; part of the result identity |

Plus optional `abc_sampling` / `semantic_sampling` dicts (temperature, top_p, top_k, repetition_penalty,
penalty_window, min_tokens, max_tokens) validated by `Sampling`. Construction raises `ValueError` on bad input,
which maps cleanly to HTTP 422.

**Environment facts on this host**

- GPU: RTX 5090, 32 GB. Driver 595. YuE2 wants BF16 and 24 GB; we have headroom.
- System Python is 3.14; `yue2-infer` pins torch 2.10.0 / transformers 4.57.6 and the uv skill pins
  Python 3.12. We use uv-managed Python 3.12.
- Model snapshots already exist under `../YuE/models/`: `YuE2-3B` (6.8 GB), `YuE2-Vae` (507 MB).
  `YuE2-Vae-legacy` (benchmark decoder) is not downloaded. SheetSage2 and MERT are present but need a
  different torch and are out of scope for this server (see §8).
- The upstream package pin used by the skill: `yue2-infer @ git+https://github.com/multimodal-art-projection/YuE@92a73cc7652fcc1f937855e4b765e0a0edd7ff2e`
  (this is the commit checked out in `../YuE`).

## 2. Goals and non-goals

Goals

- One long-lived process, pipeline loaded once, jobs queued and run serially.
- Full generation (`task: generate`) and plan-only generation (`task: plan`) so an agent can inspect and edit
  the ABC score before rendering it.
- Progress, ETA, and cancellation exposed over HTTP.
- Results retained on disk in YuE2's native artifact layout so they stay reproducible and re-decodable.
- Works offline; never downloads.
- Transcription (audio → ABC) served as well, so clients need no GPU at all.
- Compatible with `simple-ai-router`'s `busyCheck` contract.

Non-goals (for v1)

- Multiple concurrent GPU jobs, multi-GPU, vLLM backend, FP8.
- Running SheetSage2 in the server process (different torch pin). It is served, but through a
  subprocess in its own uv environment (§5.6).
- Authentication. It listens on localhost by default.

## 5. Runtime design

### 5.1 Startup (`yue2_server.py`)

1. Parse flags: `--vae standard|legacy`,
   `--budget` GiB (default from profile, else 24), `--output-dir`, `--host 127.0.0.1`, `--port 8001`,
   `--warmup/--no-warmup`, `--keep-jobs N`.
2. Set `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`.
3. `YuE2Pipeline.from_pretrained(resolve("YuE2-3B"), vae=resolve("YuE2-Vae"), device="cuda",
   memory_budget_gib=budget, local_files_only=True, progress=False)`. This verifies hashes (~10 s for 7 GB)
   and fails fast with a "run ./setup.sh" message if a snapshot is missing from the cache.
4. `--warmup` (default on): load the MoT weights onto the GPU before accepting jobs so the first request
   does not pay the load. The pipeline exposes this only via the private `_load_model()`; call it and fall
   back to a no-op if the attribute disappears in a future version. Also pre-load the VAE via
   `pipe.decode(np.zeros((1, 64, 8)))` guarded by try/except, or skip if that proves slow.
5. Construct `JobQueue(pipe, ...)`, start its worker thread, run uvicorn.

Budget comes from `yue2_common.choose_budget()`: the card's VRAM rounded, clamped to 8–28 GiB, so a 5090 gets
28 (pipeline reserves 2, leaves 26 usable, `vae_core_frames` stays 1024) and a 24 GB card gets 24. The dry
run records it in `yue2_profile.json`; command line overrides profile overrides default, like the image
server.

### 5.2 Job model (`yue2_jobs.py`)

```python
@dataclass
class Job:
    id: str                      # 12 hex chars
    request: dict                # validated SongRequest fields + sampling overrides
    task: str                    # "generate" | "plan"   ("transcribe" reserved, see §8)
    status: str = "queued"       # queued | running | done | failed | cancelled
    phase: str | None = None     # planning | semantic | synthesizing | decoding | saving
    tokens: int = 0              # tokens emitted in the current AR phase
    abc_tokens: int = 0
    semantic_tokens: int = 0
    created: float; started: float | None; finished: float | None
    error: str | None = None
    dir: Path                    # outputs/<id>
    result: dict | None = None   # result.json contents when done
    cancel: threading.Event
```

`JobQueue` holds `jobs: dict[str, Job]`, an insertion-ordered list, a `queue.Queue[str]`, and `running: str | None`.
Single worker thread:

```
loop:
  job = queue.get()
  skip if status != queued (cancelled while waiting)
  status = running; phase = planning
  try:
    if task == "plan":
        plan = pipe.plan(request=SongRequest(**req), abc_sampling=..., cancelled=job.cancel.is_set, on_token=on_token)
        plan.save(job.dir); write request.json; result = {"truncated": {"abc": plan.truncated}, ...}
    else:
        song = pipe(**req, cancelled=job.cancel.is_set, on_token=on_token)
        phase = saving
        result = song.save_artifacts(job.dir)
    status = done
  except InterruptedError:       status = cancelled
  except torch.cuda.OutOfMemoryError as e: status = failed; error = "CUDA out of memory"; empty_cache()
  except Exception as e:         status = failed; error = f"{type(e).__name__}: {e}"; write failure.json
  finally: record timings; running = None
```

`on_token(phase, token)` increments `job.tokens` and flips `job.phase` from `planning` to `semantic` when the
phase string changes. Since the pipeline offers no NAR/VAE step callback, `phase` is set to `synthesizing`
just before `pipe(...)` would enter it. That is not observable from outside `pipe()`, so for the `generate` task
the worker runs the four staged calls itself (`plan`, `generate_semantic`, `synthesize`, `decode`) and mirrors
`YuE2Pipeline.__call__` to build the `SongResult`. That gives exact phase boundaries and per-phase timings
without touching private APIs. `__call__` is ~20 lines; copying its assembly of `timing` and `request_identity`
(`identity({"request", "config", "weights"})` via `pipe.effective_config`) is straightforward and is covered
by a test that compares our `result.json["identity"]` with the CLI's for the same request.

### 5.3 Cancellation

`DELETE /jobs/{id}`: queued → `cancelled` immediately; running → set `job.cancel`, the pipeline raises
`InterruptedError` at the next token or ODE step. During `decoding` there is no hook; the job finishes decoding
(tens of seconds) and is then marked `cancelled` and its directory deleted. Status responses say
`"cancel_pending": true` in that window.

### 5.4 ETA

Measured per-phase rates, persisted in `yue2_timing.json` keyed by GPU name + budget + vae variant:

- `abc_tok_s`, `semantic_tok_s` (tokens per second, from finished jobs; exponential moving average)
- `nar_s_per_semantic_token`, `vae_s_per_latent_frame`
- `overhead_s` (model CPU↔GPU moves, saving)

Expected token counts for a queued job: ABC up to `abc_sampling.max_tokens` (4096) but typically ~1–2k;
semantic up to 9000. Use the running average of observed lengths, falling back to 1500 / 6000 before any
measurement, and report `eta_source: "prior" | "measured"` like the image server. A running job's ETA uses its
own observed rate after 50 tokens.

### 5.5 Outputs and retention

`outputs/<job_id>/` is exactly what `save_artifacts` (or `plan.save`) writes. Nothing else is stored there so
`yue2.storage.verify_result()` and the YuE skill's `run_yue2.py decode --source` keep working on our outputs.
On startup the server rescans `outputs/` and registers every directory with a valid `result.json` as a `done`
job (status only; timings not recovered) so downloads survive a restart. `--keep-jobs N` prunes the oldest
finished directories beyond N.

### 5.6 Transcription worker (SheetSage2 as a subprocess)

SheetSage2 pins torch 2.8.0 and transformers 4.45.2; YuE2 pins torch 2.10.0 and transformers 4.57.6. They
cannot share a process, so the server keeps `workers/transcribe.py`, a verbatim copy of the YuE uv skill's
helper with its PEP 723 header and lockfile, and runs it as a subprocess:

```
uv run --locked --script workers/transcribe.py <upload.wav> --output outputs/<id> \
   --task melody-full --preset default [--max-seconds N] --dtype bf16 \
   --model models/SheetSage2 --base-model models/MERT-v2-FullSong --offline --device cuda
```

Job flow in the same worker thread as generation:

1. The upload handler writes the file to `outputs/<id>/upload/<original name>` (size-capped, extension
   checked against a short list: wav, flac, mp3, ogg, m4a) and queues the job.
2. **GPU handoff.** Before launching, the worker moves the YuE2 MoT model to CPU if it is resident
   (`pipe._model.to("cpu")`, wrapped like the warmup) and calls `torch.cuda.empty_cache()`. After a
   generation job both models are already on CPU, so this usually costs nothing; after warmup it costs one
   7 GB transfer. SheetSage2 plus MERT need roughly 4–6 GB.
3. `subprocess.Popen` with `HF_HUB_OFFLINE=1`, stdout/stderr captured to `outputs/<id>/worker.log`.
   Progress is phase-only: `loading` until `model_provenance.json` appears, then `transcribing`.
4. Cancellation sends SIGTERM, then SIGKILL after 10 s. Exit code 0 plus a `transcription_manifest.json`
   with `status: complete` marks the job `done`; anything else is `failed` with the last stderr line and
   `failure.json` if the worker wrote one.
5. `artifacts` in the status view is the manifest's file list plus the manifest itself. `/jobs/{id}/score`
   serves `score.abc`. The upload directory is deleted once the job is terminal.

Loading SheetSage2 and MERT per job costs tens of seconds; measured `load_s` and `s_per_audio_second` feed
the ETA the same way generation timings do. The environment is built once by `setup.sh` (`uv sync
--script workers/transcribe.py --locked`), so per-job startup is Python import time, not package install.

### 5.7 Lyrics recognition worker (Qwen3-ASR as a subprocess)

Why Qwen3-ASR-1.7B: WildSongBench's own PER evaluator is built on it, and its technical report shows the
best published results on sung-lyrics sets (M4Singer 5.98, MIR-1k-vocal 6.25, Opencpop 3.08, Popcs 8.52 WER)
and full songs with backing (EntireSongs en 14.6 / zh 13.9), where Whisper-large-v3 degrades. Apache 2.0,
52 languages, 2B params in bf16 (~4.7 GB), released 2026-01-29; pinned to Hub main of 2026-09-25,
`7278e1e7`. The general-speech leaderboard leaders (Granite Speech, Canary-Qwen) are not trained for
singing and are not multilingual in the way a Mandarin/English lyric-translation check needs.

`qwen-asr` 0.0.6 pins `accelerate==1.12.0` while `yue2-infer` pins 1.13.0, so it cannot share the server
process. `workers/lyrics.py` (PEP 723, locked: qwen-asr, torch 2.10 cu128, g2p_en, pypinyin) runs through
the same `_run_worker` path as SheetSage2: MoT offloaded, `loading` until `model_provenance.json`, then
`recognizing`, SIGTERM on cancel, manifest on success. Input is either the uploaded file or `source_job`'s
`audio.flac`. Scoring is the worker's documented recipe (normalize, units, ARPAbet / pinyin phonemes,
Levenshtein), reported per pass with the lowest-PER pass selected, mirroring the benchmark's best-of-N
shape without claiming its undisclosed evaluator. `setup.sh` fetches the nltk data g2p_en needs
(`lyrics.py --prepare`) so the worker runs offline.

## 6. HTTP API

Four operations cover every workflow in the agent skill. JSON tasks go through `POST /jobs` with a `task`
field; transcription goes through `POST /jobs/transcribe` because it carries an audio upload. All of them
are long-running GPU jobs that share one queue, and the client side never needs a GPU.

| `task` | Operation | Inputs | Output | Phase |
|---|---|---|---|---|
| `plan` | text → ABC | style, lyrics, `cot=full\|melody` | `score.abc`, `plan.json` | 4 |
| `generate` | text → audio, or ABC → audio | style, lyrics, `cot`, optional `abc` | `audio.flac` plus score and artifacts | 2 |
| `decode` | latents → audio again | `source_job`, `vae=standard\|legacy` | new `audio.flac` + full artifact set, latents unchanged | 6 |
| `transcribe` | audio → ABC | multipart audio file, `task=full\|melody-full\|melody-vocal`, `preset`, `max_seconds`, `dtype` | `score.abc`, MIDI, LAB annotations, `transcription_manifest.json` | 5, subprocess |
| `lyrics` | audio → sung-lyrics transcript, scored | `source_job` or multipart audio; `lyrics` reference, `language`, `passes` | `transcript.txt`, `lyrics_asr.json` (WER/CER, PER per pass), `lyrics_manifest.json` | 5b, subprocess |

`cot=off` has no score, so text → ABC exists only for `full` and `melody`; `generate` with `cot=off` is a
pure text → audio call. ABC tooling (chord stripping, invariant checks, comparisons) ships with the skill's
`abc_tools.py` and stays on the client side.

| Method, path | Purpose |
|---|---|
| `POST /jobs` | Submit a JSON task (`generate`, `plan`, `decode`). `202` with `{id, status, position, eta_s, task}` |
| `POST /jobs/transcribe` | Submit a transcription: multipart form with `audio` (file, ≤ `--max-upload-mb`, default 200) and text fields `task`, `preset`, `max_seconds`, `dtype`. Same `202` body |
| `GET /jobs` | All jobs newest first (summary view) |
| `GET /jobs/{id}` | Status view (below) |
| `GET /jobs/{id}/wait?timeout=N` | Long-poll: returns when the job finishes or after N seconds (default 300, max 3600) |
| `DELETE /jobs/{id}` | Cancel |
| `GET /jobs/{id}/audio` | `audio.mp3` by default (ffmpeg, libmp3lame VBR 2, made at job completion and listed in `artifacts`); `?format=flac` is the stored lossless artifact, `?format=wav` re-encodes with soundfile. `409` until done; `404` for plan/transcribe jobs |
| `GET /jobs/{id}/score` | `score.abc` as `text/plain` (`404` when `cot=off`); works for transcription jobs too |
| `GET /jobs/{id}/artifacts/{name}` | Any file the job's status view lists under `artifacts` (everything `save_artifacts` or `plan.save` wrote: `result.json`, `plan.json`, `plan_manifest.json`, `score.abc`, `audio.flac`, `request.json`, `config.json`, `prefix.npy`, `abc_tokens.npy`, `semantic.npy`, `latent.npy`). Names are matched against that list, never against the filesystem |
| `GET /health` | `{status, running, queued, model, vae, weights identities, gpu, budget_gib, timings, eta_source}` |

`running` is the running job id or `null` and `queued` is an integer, which is what `simple-ai-router`'s
`busyCheck.fields: [running, queued]` expects.

Submit body (pydantic `SubmitRequest`):

```json
{
  "style": "English, warm piano pop, expressive female voice, 88 BPM",
  "lyrics": "[Verse]\n...\n[Chorus]\n...",
  "cot": "full",
  "seed": 831001,
  "abc": null,
  "cfg_scale": null,
  "id": "city_lights",
  "abc_sampling": {"max_tokens": 4096},
  "semantic_sampling": {"max_tokens": 9000},
  "task": "generate"
}
```

Validation: pydantic checks shape and types, then the handler constructs `SongRequest(...)` and
`resolve_sampling(...)` and turns `ValueError`/`TypeError` into `422` with the library's message. `seed` is
random when omitted and echoed back in the status, matching the image server's behaviour.

**Asynchronous by construction.** `POST /jobs` never waits for the GPU: it returns `202` in milliseconds and
the worker thread runs the job later. Torch releases the GIL inside CUDA kernels, so the event loop keeps
serving status, downloads and new submissions while a song renders. Clients get results three ways:

The intended client is the agent skill's bash scripts calling `curl`, so delivery is pull-only:

- **Poll** `GET /jobs/{id}` until `done`, then download.
- **Long-poll** `GET /jobs/{id}/wait?timeout=300`: blocks up to `timeout` seconds and returns the status
  view as soon as the job reaches a terminal state, or the current view on timeout. One `curl` per job
  instead of a sleep loop; scripts re-issue it on timeout. Implemented with an `asyncio.Event` per job
  set by the worker, so it costs nothing while waiting.
- No webhooks and no push: the server never opens outbound connections.

Status view:

```json
{
  "id": "e3969fd18827", "status": "running", "task": "generate",
  "phase": "semantic", "tokens": 2310, "abc_tokens": 1420,
  "position": 0, "eta_s": 210, "elapsed_s": 95,
  "request": {"...": "..."}, "seed": 831001,
  "truncated": null, "audio_seconds": null, "identity": null,
  "audio_url": null, "score_url": "/jobs/e3969fd18827/score", "error": null,
  "artifacts": null
}
```

When done, `truncated`, `audio_seconds`, `identity`, `timing` and the URLs are filled from `result.json`,
and `artifacts` is the list of file names in the job directory (from `result.json["artifacts"]` plus
`result.json` itself for `generate`/`decode`, from `plan_manifest.json` plus itself for `plan`). The skill's
`run_yue2.py` downloads exactly that list and re-verifies the hashes locally.
The `truncated` flags matter: a song that hit the 9000-token limit is playable but incomplete and the client
should know.

Editing workflow this enables, with no extra endpoints:

1. `POST /jobs {task: "plan", ...}` → `GET /jobs/{id}/score`
2. Edit the ABC (agent or human).
3. `POST /jobs {task: "generate", abc: "<edited>", cot: "full", ...}`

## 8. Risks and open points

- **Per-song latency is unmeasured.** Up to 4096 ABC + 9000 semantic tokens autoregressively, then NAR flow
  matching (32 midpoint steps) and VAE decode. Expect several minutes per song on the 5090. Phase 2's first
  real run sets the priors; the ETA model is the mitigation, not a speedup.
- **`__call__` mirroring.** Running the staged calls ourselves duplicates ~20 lines of upstream assembly.
  Pinning the exact upstream commit and the identity-equality test guard against drift.
- **`_load_model()` warmup** is a private API. It is wrapped so a rename only costs first-job latency.
- **No cancel during VAE decode.** Documented; the window is short.
- **VRAM.** Only one process may own the GPU. If `qwen-image-server` or another model is running, the router
  must swap them; with `simple-ai-router` that is already the design. Do not run both servers by hand at once.
- **Model licence.** Weights are CC BY-NC 4.0; the server does not change that and should not be exposed
  publicly for commercial use.
- **Truncation.** Long lyrics can exceed the semantic token limit. The API surfaces `truncated` and the
  README should suggest keeping lyrics to typical song length.
- **SheetSage2 subprocess.** Its remote code runs with `trust_remote_code=True` at the pinned commit
  (`eab522a`); review it before first use, as the YuE skills already require. Per-job model loading adds tens
  of seconds and the `uv` environment must be built by `setup.sh` before the first request, otherwise the
  first transcription would try to resolve packages. `ffmpeg` must be on the server's `PATH`.
- **Upload size.** Full songs as WAV are tens of MB; the multipart cap defaults to 200 MB and rejects larger
  files with `413` before anything is written.

Contract the script pins down (the server must satisfy these, and `tests/test_api.py` checks them):

- `GET /health` returns JSON and is the reachability check.
- `POST /jobs` accepts `{task, style, lyrics, cot, seed, abc, cfg_scale, id, abc_sampling, semantic_sampling}`
  and for `decode` `{task, source_job, vae}`; returns `202` with `id`. Validation errors are `422` with a
  `detail` string, which the script surfaces verbatim.
- `GET /jobs/{id}/wait?timeout=N` returns the status view; `status` is one of
  `queued | running | done | failed | cancelled`; a done view carries `artifacts: [names]`, a failed view
  carries `error`.
- `GET /jobs/{id}/artifacts/{name}` streams each listed file unchanged, so local SHA-256 checks pass.
- `DELETE /jobs/{id}` cancels and is idempotent.
- `POST /jobs/transcribe` accepts multipart with an `audio` part and text parts `task`, `preset`,
  `max_seconds`, `dtype`; returns the same `202` body. A done view lists the transcription artifacts.

Acceptance for phase 2 becomes: `python skills/yue2-music-server/scripts/run_yue2.py generate --request
skills/yue2-music-server/assets/prompt.json --output outputs/skill-check` exits 0 with a verified
`audio.mp3`, `audio.flac` and `score.abc`.
